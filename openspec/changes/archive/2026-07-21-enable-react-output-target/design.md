## Context

`packages/form-components` builds Stencil web components and currently emits two production targets: `dist` (lazy-loaded) and `dist-custom-elements` (tree-shakeable). React consumers can already import the custom elements build, but they must register elements themselves and pass props/events as DOM attributes/listeners — there is no typed React API. The Stencil config already documents intent to add `@stencil/react-output-target`. React 18+ is the assumed peer; Preact consumers are expected to alias `react`/`react-dom` to `preact/compat`.

## Goals / Non-Goals

**Goals:**
- Generate typed React wrapper components for every Stencil component in the library.
- Ship the wrappers via a new `exports` entry on `@webmobix/form-components` so React apps import idiomatic components with proper prop typing and event handling.
- Keep the build additive: existing `dist`, `dist-custom-elements`, `loader`, and `docs-readme` outputs remain unchanged.
- Support Preact consumers transparently via `preact/compat` aliasing (no separate Preact target).

**Non-Goals:**
- Hand-rolling a custom Preact output target.
- Changing the web component source or component APIs.
- Adding a separate publishable package for React (wrappers live inside `@webmobix/form-components`).
- Supporting React versions older than 18.

## Decisions

### Decision 1: Use `@stencil/react-output-target` with `dist-custom-elements` as the underlying build
**Rationale:** The official Stencil React target is purpose-built, maintained, and produces typed wrappers with correct event/prop binding. It relies on the `dist-custom-elements` build that we already produce. Hand-rolling wrappers would duplicate this work and drift from Stencil internals.
**Alternatives considered:** (a) Manual React wrappers using `createComponent` patterns — rejected as maintenance burden and risk of prop/event binding bugs. (b) Waiting for `@preact/stencil-output-target` — does not exist; the proposal explicitly notes Preact uses `react/compat` aliasing on the React output.

### Decision 2: Output location — `packages/form-components/react/`
**Rationale:** Co-locating generated wrappers inside the existing package avoids a new package and keeps `exports` mapping simple. The directory is generated by the Stencil build and added to `files` for publishing.
**Alternatives considered:** (a) A new sibling package `@webmobix/form-components-react` — rejected for now; adds publishing/dependency overhead with no consumer benefit at this stage. Can be split out later if needed.

### Decision 3: Export path `./react`
**Rationale:** A subpath export keeps the React surface opt-in — importing `@webmobix/form-components` does not pull React into the module graph. `@webmobix/form-components/react` resolves to the generated `index.js` with `types` pointing at generated `.d.ts`.
**Alternatives considered:** (a) Re-export from the main entry — rejected because it forces React as a hard runtime dependency for plain-HTML consumers.

### Decision 4: `react` and `react-dom` as peer dependencies
**Rationale:** Wrappers must use the consumer's React instance to avoid duplicate React copies and hook state issues. Peer deps encode this contract and let the consumer pick React 18+.
**Alternatives considered:** (a) Bundling React — rejected (duplicate-instance bugs).

### Decision 5: `includeImportSymbols: true`, `customElementsExportBehavior` unchanged
**Rationale:** The React target consumes the custom-elements build's exported component classes. The existing `customElementsExportBehavior: 'auto-define-custom-elements'` is preserved so wrappers can render without host apps manually defining elements.

## Risks / Trade-offs

- **[Risk] Generated wrappers may lag Stencil API changes** → Mitigation: pin `@stencil/react-output-target` to a version range compatible with `@stencil/core` (^4.27 || ^5), bump together.
- **[Risk] Preact consumers hit edge cases with `preact/compat`** → Mitigation: documented as best-effort; not guaranteed. Call this out in the package README and in the design non-goals.
- **[Risk] Build time increases** → Mitigation: minor; acceptable. No parallelization changes needed.
- **[Trade-off] Wrappers live inside the same package rather than a dedicated one** → Simpler now, but splitting later would be a breaking change to import paths. Accepted for now; can be revisited when a standalone React package is warranted.
- **[Risk] TypeScript path resolution for `./react` types** → Mitigation: verify `exports` + `typesVersions`/`types` mapping; add a smoke test import in a build step.

## Migration Plan

1. Add dependency and config (additive); no existing consumer behavior changes.
2. Build once locally and verify `react/` is emitted with `index.d.ts`.
3. Publish new version; document the `./react` import path in the package README.
4. Rollback: remove the output target block and the `./react` export entry; rebuild. Existing consumers are unaffected.

## Open Questions

- Should the React export also re-export the loader for SSR scenarios? Deferred until an SSR consumer exists.
- Naming of the generated component export aliases (Stencil uses `ComponentName` PascalCase by default) — accept defaults unless collision found.
